# RAG 全流程与实现

## RAG 是什么
RAG（Retrieval-Augmented Generation，检索增强生成）是把"检索"和"生成"结合的
技术。在 LLM 生成回答前，先从知识库检索相关内容，拼进 Prompt，让 LLM 基于真实
资料回答。解决 LLM 知识过时、无法访问私有数据的问题。

## RAG 核心流程
### 索引（离线）
1. 加载文档
2. 切分（每块 300-500 字，重叠 50 字）
3. Embedding 转成向量
4. 存入向量数据库

### 检索（在线）
1. 用户问题用同一个 embedding 模型转向量
2. 在向量库用余弦相似度找 Top-K 相近片段
3. 返回片段内容

### 生成
1. 把检索到的片段拼进 System Prompt
2. LLM 基于资料回答
3. 资料没有就正常回答

## Embedding 是什么
把文本转成固定长度向量的技术。语义相近的文本，向量距离也近。
我用的模型是 BAAI/bge-small-zh-v1.5，中文效果好，只有 95MB。

## 向量检索怎么工作
1. 所有文档块转成向量，存进向量数据库
2. 查询时把问题转成向量
3. 计算查询向量和所有文档向量的余弦相似度
4. 返回相似度最高的 Top-K

## 上下文拼接
把检索到的 Top-K 片段拼成一段文本，加进 System Prompt，明确告诉 LLM
"以下是参考资料，请基于这些回答"。

## 为什么用 ChromaDB
轻量、本地、零配置、支持持久化和余弦相似度检索。适合中小规模应用。
对比 FAISS 要自己管 ID 映射，对比 Milvus 要跑服务。

## 为什么用 BGE
BAAI/bge-small-zh-v1.5 是中文场景性价比最高的轻量模型。95MB，速度快，
中文语义相似度效果好，本地部署不需要 API 调用。

## RAG 和微调的区别
微调：把知识训练进模型权重，成本高、更新难。
RAG：知识存在外部库，检索时拼接，成本低、更新方便、更透明。

## 我的 RAG 怎么实现的
用 ChromaDB 做向量库，BGE 中文模型做 embedding。文档先切分成 300-500 字的片段，
用 embedding 转成向量存入 ChromaDB；查询时把问题转向量，用余弦相似度找 Top-3
相关片段，拼进 System Prompt 让 LLM 基于资料回答。
